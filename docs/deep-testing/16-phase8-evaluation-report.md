## 2. Implemented Security Controls & Architectural Hardening

### 2.1 Transport & HTTP Security Headers
- Added defense-in-depth security hardening middleware to `backend/app/main.py`:
  - `X-Content-Type-Options: nosniff`: Prevents MIME-type sniffing and drive-by download attacks.
  - `X-Frame-Options: DENY`: Prevents UI redressing and clickjacking attacks.
  - `X-XSS-Protection: 1; mode=block`: Activates browser reflected XSS filters.
  - `Referrer-Policy: strict-origin-when-cross-origin`: Restricts referrer information leakage.
  - `Permissions-Policy: geolocation=(), camera=(), microphone=()`: Disables unneeded browser APIs.
  - `Content-Security-Policy`: Restricts resource fetching to self, inline styles, and explicit local API endpoints; enforces `frame-ancestors 'none'`.

### 2.2 Resource Protection & Denial-of-Service Resistance
- Ingress payload size limit: Request bodies with `Content-Length > 2MB` are intercepted by middleware and rejected with `HTTP 413 Payload Too Large` before memory buffering.
- IP-based sliding window rate limiter: Limits non-loopback clients to 30 requests/minute per IP.

### 2.3 Authentication & Session Security
- Passwords hashed via PBKDF2-HMAC-SHA256 with cryptographically random 16-byte salts and high iteration counts. Plaintext passwords are never stored or logged.
- Brute-force mitigation: Exactly 5 consecutive failed login attempts trigger an automatic 15-minute account lockout (`HTTP 423 Locked`).
- Non-existent usernames execute dummy password verifications to prevent timing-based user enumeration.
- Session tokens are random 256-bit hexadecimal strings invalidated immediately upon logout (`POST /api/auth/logout`).
- Multi-factor authentication: Fully operational RFC 6238 TOTP enrollment with base32 secret generation, `otpauth://` QR URI, and 5 single-use recovery codes.

### 2.4 Zero-Trust RBAC & Insecure Direct Object Reference (IDOR) Defense
- Backend independently enforces permissions on every endpoint via `require_permission()`.
- Analysts cannot access user management (`/api/users`), SIEM security events (`/api/security/events`), security alerts (`/api/security/alerts`), or incident controls (`/api/incident/transition`) — all return `HTTP 403 Forbidden`.
- Analysts cannot inspect or verify receipts generated by other users; only the receipt creator or authorized auditors/data stewards can verify them.

### 2.5 Data Vault Isolation & Injection Defense
- Raw rows in `healthcare_vault` and `financial_vault` are never accessible via any REST API endpoint.
- All analytical queries are restricted to pre-approved categorical fields and enum values. Arbitrary SQL, SQL injection payloads, and path traversal strings (`../../../etc/passwd`) are rejected fail-closed with `HTTP 400 Bad Request`.
- Operator normalization canonicalizes both `=` and `equals` to identical SHA-256 fingerprints.

### 2.6 Differential Privacy & Micro-Epsilon Concurrency
- Analytical releases use the Laplace mechanism calibrated to $\Delta f = 1.0$ per distinct privacy unit (`patient_id` or `customer_id`).
- Concurrency protection: `execute_query_pipeline` acquires an atomic SQLite transaction lock (`BEGIN IMMEDIATE;`) before reading or modifying the ledger, preventing double-spend race conditions.
- Cumulative budget exhaustion fails closed with `HTTP 429 Too Many Requests`.
- Exact query replays cost $0.00\,\epsilon$ and return cached releases without consuming budget.

### 2.7 Cryptographic Release Accountability
- Every query release produces a tamper-evident Privacy Receipt signed with Ed25519 using enclave keys (`TRUSTED_KEY_ID = "ED25519-ENCLAVE-2026-V1"`).
- Receipts contain canonical SHA-256 hashes linking release telemetry to an immutable audit trail.
- Every audit entry is mathematically linked via SHA-256 hash chaining to the root genesis block (`HOTFIX-GENESIS-UG59-MVP-AUDIT-ROOT`). Any database record tampering is detected immediately by `GET /api/audit/verify`.

### 2.8 Disaster Recovery, Backup & Anti-Rollback Reconciliation
- Implemented `backend/app/services/backup_service.py` and CLI utility `scripts/backup_and_recovery.py`:
  - `create_database_backup()`: Uses SQLite's online atomic backup API (`sqlite3.Connection.backup()`) to create consistent point-in-time snapshots during active reads and writes. Generates a SHA-256 checksum and a JSON metadata sidecar (`BKP-<timestamp>-<token>`).
  - `verify_backup_integrity()`: Validates file existence, SHA-256 checksum match, SQLite `PRAGMA integrity_check`, foreign key constraints, and cryptographic audit log validity.
  - `restore_database_backup()`: Safely restores to target path with **Anti-Rollback Privacy Reconciliation**:
    - Calculates total `epsilon_micro` released across all historical queries.
    - If `spent_micro_epsilon` in `budget_ledger` is less than historical releases (indicating an attacker attempted to roll back an exhausted budget), the restore engine automatically reconciles `spent_micro_epsilon` to the authoritative release total and caps `remaining_micro_epsilon`.

## 6. Documented Residual Risks & Non-Claims

1. **Non-Claim of Mathematical Infallibility**: SentinelVault does not claim mathematical infallibility or complete immunity from hardware-level side-channel attacks, kernel compromise, or unauthenticated physical memory inspection.
2. **Local Loopback Trust**: For local development and demonstration testing, loopback addresses (`127.0.0.1`, `localhost`) are granted permissive rate limit ceilings. In enterprise deployments, `HOTFIX_ENV=production` must enforce strict exterior IP limits.
3. **Key Storage**: Ed25519 signing keys are protected with filesystem ACLs in `backend/keys/`. For enterprise government deployments, migration to a hardware security module (HSM) or cloud KMS (AWS KMS / Google Cloud KMS) is recommended.
