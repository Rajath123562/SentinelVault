4. **Differential Privacy Pipeline (`backend/app/services/privacy_engine.py`)**:
   - Real Laplace noise mechanism via IBM `diffprivlib` with CSPRNG fallback.
   - Bounded integer post-processing ($\ge 0$).
5. **Restricted Query Engine (`backend/app/services/query_engine.py`)**:
   - Allowlist query grammar (`COUNT_DISTINCT_PRIVACY_UNITS` only).
   - Global sensitivity bounded to $\Delta f = 1.0$ by counting distinct privacy units (`patient_id`, `customer_id`).
   - Zero-cost caching for repeated identical queries and idempotency protection.
6. **Cryptographic Receipts & Audit (`backend/app/services/crypto_audit.py`)**:
   - Self-contained verifiable Privacy Receipts with SHA-256 audit entry hash pointers.
   - Authentic Ed25519 digital signatures generated by gateway authority keypair.
   - Append-only SHA-256 hash-chained audit ledger with full verification endpoint (`/api/audit/verify`).
7. **Web Frontend (`frontend/src/`)**:
   - React 19 + TypeScript + Vite + Tailwind CSS dashboard.
   - Views: Authentication (View A), Analytics Dashboard (View B), Privacy Receipt Inspector (View C), Audit & Utility Evaluation (View D), System Architecture.

## 3. Missing or Incomplete Foundation Requirements (Phase 2 Scope)

While a preliminary authentication prototype exists, the following enterprise security controls are required for Phase 2:

1. **Centralized Zero-Trust Authorization & Granular Permissions**:
   - Current endpoints check high-level roles (`analyst`, `data_steward`, `auditor`).
   - Phase 2 must introduce explicit permission IDs (`system.status.read`, `dataset.metadata.read`, `dataset.query.execute`, `receipt.read.own`, `receipt.read.authorized`, `audit.verify`, `security.events.read`, `security.policy.manage`, `user.manage`).
   - Object-level authorization: An Analyst must only access receipts they created (`receipt.user_id == current_user`), while Auditors can inspect all receipts.
2. **Network-Level and Progressive Rate Limiting**:
   - Current lockout is account-level only.
   - Phase 2 must implement client IP-level rate limiting to defend against distributed and high-frequency brute-force attempts.
3. **Multi-Factor Authentication (MFA / TOTP)**:
   - Privileged roles (`data_steward`, `auditor`) require RFC 6238 TOTP enrolment, verification, and backup recovery codes.
4. **Security Event Logging Ledger**:
   - Formal `security_events` table recording authentication and authorization attempts, outcomes, and actors without leaking secrets.
5. **Comprehensive Browser-Tampering Defenses**:
   - Systematic automated tests verifying that client-modified parameters (`role="Admin"`, `authorized=true`, client-side counters, fabricated headers) are strictly ignored by the authoritative backend.
6. **Administrative Session Management**:
   - Explicit session revocation API and session lifecycle auditing.

## 5. Expected Compatibility Risks & Mitigation

1. **Risk**: Modifying the `users` and `sessions` database schema could break existing queries or tests.
   * *Mitigation*: Use SQLite `ALTER TABLE` or additive columns with default values (`user_id`, `status`, `last_login_at`, `mfa_enabled`, `mfa_secret`, `revoked_at`) ensuring backwards compatibility with existing Phase 1 queries.
2. **Risk**: Tightening receipt ownership checks could break existing receipt inspection tests.
   * *Mitigation*: Ensure test fixtures execute queries under the matching user identity or use auditor credentials for cross-user audits.
3. **Risk**: Rate-limiting during automated testing could trigger false-positive 429 errors.
   * *Mitigation*: Support configurable rate-limit thresholds and test fixtures that isolate or reset rate-limiting windows between test runs.
